# 企业选股产品与后台研究：产品设计 v0.3

日期：2026-09-20。状态：设计研究稿，未实现新系统。本文落实已确认的方向：企业日常使用选股功能，研究过程在后台；页面细节和分期是本次建议。

本文替代 v0.2 的第三节「系统界面」与第四节「最小可交付版本」。v0.1 的时间隔离、交易评价原则及 v0.2 的三条研究反馈机制继续保留。此前三张视觉概念稿不作为实现依据。

## 1. 产品定位与本次研究结论

交付物是「具有持续优化能力的多因子选股系统」。业务用户用已经发布的方案生成并使用候选股票名单；研究维护者通过强化学习与组合优化产生候选方案，经验证后发布。两类工作共用数据、评分和版本体系，但各自有清楚的操作入口。

首版按日频、收盘后数据完成再评分设计。输出供后续交易决策使用的股票排名和候选名单，不包含自动下单。当前研究基准是明确执行规则的 Top K，不将其表现称为企业私有策略的表现。

公开实现提供了两项可借鉴的机制：MLflow 将实验来源、模型版本与正在使用的版本引用连接起来；Qlib 区分模型准备、预测更新和信号生成，并记录模型何时上线。它们支持本项目采用「研究产出 → 发布版本 → 日常评分」的边界；不是本项目必须安装这些框架的理由。[MLflow 模型注册表](https://mlflow.org/docs/latest/ml/model-registry/)，[Qlib Online Serving](https://qlib.readthedocs.io/en/latest/component/online.html)。

## 2. 三种组织方式

| 方式 | 使用特点 | 取舍 |
|---|---|---|
| 一个系统，业务工作台与管理工作区分开（推荐） | 企业直接进入选股；维护者进入管理工作区处理研究、数据和发布 | 共用资产与核心计算，交付规模适中；需要真正的服务端权限和任务隔离 |
| 选股应用与研究平台完全独立 | 两个部署，通过模型包/API 交接 | 企业与研究团队分离时适用；首版会增加部署、认证与数据同步负担 |
| 全功能放在同一导航，用折叠隐藏 | 容易利用旧菜单 | 用户仍需理解内部阶段，缺少发布边界；不能解决当前问题 |

推荐第一种。一个系统不等于一个执行进程：研究耗时任务与日常评分任务分开调度并限制研究资源占用。首版可以单机部署，不先建设微服务集群。

## 3. 企业用户的日常流程

用户打开系统 → 看见最近一份有效名单及其真实数据日期 → 查看排名变化与评分依据 → 导出名单。

常规使用不要求先创建因子、挑选回测目录、调整权重。新数据通过检查后，后台可以自动生成常规名单；页面保留「生成名单」供手动触发或失败后重试。首版先打通手动执行，同一条服务流程再增加系统内定时任务。本设计不创建任何实际定时任务。

没有可用方案时，业务页显示「尚未配置可用选股方案」，由维护者配置；不能把业务用户引导到 PPO 训练。没有新数据时继续展示上一份结果并突出日期，不能把它标成今日名单。

## 4. 企业前端：三个业务入口

### 4.1 选股工作台（默认首页）

页面优先放决策需要的信息，采用稳定的导航、紧凑工具栏、主表格与股票详情抽屉。

| 区域 | 内容及行为 |
|---|---|
| 页头 | 当前选股方案、实际数据日期、生成时间、就绪/待更新/生成中/失败状态 |
| 操作栏 | 生成名单、导出名单；多个已发布方案存在时才显示方案选择 |
| 结果概览 | 入选数量、符合规则数量、较上一份的新增/移出数量；无可比记录时不计算变化 |
| 主表格 | 排名、代码、名称、行业、综合得分、排名变化、入选状态；价格需要标明对应日期 |
| 表内筛选 | 代码/名称搜索、行业筛选、查看入选/全部已评分股票；只改变视图 |
| 股票详情 | 得分组成、主要正负贡献、历史排名、数据缺失及入选/未入选原因 |
| 方案摘要 | 适用范围、研究与发布版本、评分口径；方法详情按需展开 |

数据来源缺少名称或行业时显示未提供，不根据代码推造信息。综合得分是同一评分截面的排序依据，不标成上涨概率或预期收益；跨日看排名/分位变化，避免暗示原始得分完全可比。贡献解释说明计算来源，不把相关信号写成股价涨跌的因果理由。

「较上一份」只比较同方案定义、同版本和同配置的最近记录；版本切换时显示换版标记，不将所有名单变化归因于市场。允许另行查看跨版本差异，但标出差异来源。

主视图以候选名单为中心，不放训练奖励曲线、GPU 使用率、全流程架构图、累计生成因子数。运行状态在页头局部显示，任务错误详情在需要时展开。

### 4.2 选股记录

按日期查看当时实际生成和保存的名单，显示方案版本、数据版本、生成时间、选择配置以及导出记录。详情沿用工作台的表格和抽屉，避免另造一套结果界面。

历史档案不可用新模型覆盖。使用新模型计算旧日期必须新建「历史重算」记录，不能冒充当时已经发出的名单，也不能将它混入发布后表现。

名单增加/移出只表示候选资格变化；没有真实持仓和成交数据时，不生成「必须买入/卖出」指令。

### 4.3 方案表现

回答「当前方案按什么规则验证、最近是否正常」，提供简明规则摘要和表现。分别展示历史验证回测与发布后按预定 Top K 规则模拟跟踪的结果，不默认拼成一条曲线。

发布后跟踪沿用真实时点发出的名单和固定成交、成本口径；结果应称模拟跟踪，不能称企业实盘收益。没有足够观察期或必要价格数据时显示未成熟/暂不可计算。换版本时标记边界；组合多个版本的运行轨迹必须明确称为系统历史运行表现。

首版可以只有已完成的验证摘要与发布信息；发布后模拟跟踪在交易核算验证完成后上线，不能为了页面完整展示占位收益曲线。

数据状态在所有业务页面可见；完整连接配置与同步任务放管理工作区。「说明/帮助」包含方法介绍；公式逐层解释，不让用户在操作前读完研究报告。

## 5. 选股方案是研究与使用之间的交付单位

企业界面叫「选股方案」，维护界面可同时显示模型版本。它是可执行、可追溯的包，不只是一个权重 CSV。

方案至少包含：

- 因子表达式、评分权重、算子与计算实现版本。
- 字段需求、单位、复权与时点口径、回看长度、缺失和异常处理。
- 评分股票范围的规则、标准化范围、可选资格规则及其执行顺序。
- 候选数量与可选配置、固定 Top K 验证规则、适用范围。
- 研究截止时间、形成时间、验证报告、来源实验、包校验值。

每天解析股票范围并保存实际成员快照。方案的股票池规则固定，成员可以按当日已知信息变化；不能用今天股票名单回填所有历史日期。若暂时只支持固定成员，应明确标为固定股票池方案，不能声称覆盖全 A 股动态范围。

三个对象保持独立：研究实验记录「如何得到方案」；发布版本记录「允许使用什么」；选股记录记录「某时点实际用了什么」。PPO 检查点用于研究恢复，日常评分只需可执行因子与组合包，无须启动 PPO。

## 6. 普通用户能改什么

| 操作 | 处理方式 |
|---|---|
| 搜索、排序查看、行业视图筛选 | 改变显示，不改变原始评分、入选名单和方案配置 |
| 只导出所见行 | 文件标明筛选条件和「名单子集」，不改原始档案 |
| 查看前 N 名 | 允许浏览已有排名；与方案正式 Top K 名单明确区分 |
| 改变正式候选数量或附加排除条件 | 仅开放方案预先声明且验证过的配置；保存配置标识，对应展示验证结果 |
| 改评分股票池、标准化、因子权重或风险约束 | 形成新的研究/验证配置，由维护者处理，不沿用旧验证结论 |

首版推荐每个方案固定一套正式 Top K 配置，减少不必要的自由参数。用户可浏览更多股票并导出排名，但不能把 Top 100 的查看操作称为已经验证过的 Top 100 策略。

特别注意横截面计算：页面过滤行业后，不在剩余股票上重新计算标准化分数。评分范围与候选资格的处理顺序由方案固定，研究与日常选股必须一致。

## 7. 管理工作区及反馈闭环

维护者入口位于辅助导航，包含数据接入、研究任务、方案版本与发布、运行记录。角色限制同时在服务端执行；仅隐藏菜单不构成权限控制。业务用户不能直接调用训练、改权重或发布接口。

研究任务内部保留 v0.2 的三条反馈：质量评价改变生成反馈；组合表现改变后续组合搜索；相对基线的组合增量表现进入 PPO 奖励并更新生成器。研究人员按需查看轨迹、对照、失败候选和检查点。主业务页只展示最终可用方案及其结果。

增加应用反馈链：真实时点名单 → 后续数据成熟 → 按预定规则模拟评价 → 周期性研究或退化检查 → 候选新方案 → 验证与发布。

这条应用链的触发动作首版是建立带原因和数据截止时间的研究任务，不直接在线改正在使用的权重。后续将已成熟数据纳入新研究窗口时需登记其用途；反复使用的发布验证数据属于模型选择数据，不能再声称是未触碰的最终测试集。最终研究测试保留独立锁定窗口或事先规定的向前评估协议。

系统运行并不保证每轮效果都提高。质量失败、候选退化、验证不通过都保留记录；没有合格新版本时继续使用既有可用版本。企业交易反馈只有在实际接入并约定口径后才能纳入评价，不能从名单点击或导出行为推断投资收益。

## 8. 发布、换版与回退

候选 → 验证通过/验证不通过；验证通过后由维护者发布 → 生效；之后可被新版本替代或停用。验证通过不等于立刻替换正在使用的方案。

发布前按预先登记的协议检查：数据与实现可复现、评分与回测口径一致、字段可用性、验证区间与比较基线、收益风险目标、覆盖率及运行开销。阈值由具体实验协议声明，本稿不编造适用于所有策略的提升百分比。

生效时间明确到下一次评分任务。任务启动时锁定方案版本与数据快照，中途发布不影响该任务。发布日志记录操作者、旧版本、新版本、生效时间和验证依据。

回退只影响之后的任务，不改历史结果。旧版本也必须通过当前数据兼容性检查；若均不可用，展示上一次有效结果及异常状态，暂停生成新的正式名单。首版采用维护者发布；自动发布作为以后单独验证的能力，不影响后台研究自动迭代。

## 9. 数据更新决定是否真正可用

最新缓存日期不能只取所有股票的最大日期。应结合交易日历、数据源完成状态、所需字段及覆盖情况确定可评分时点；允许的例外写入方案，禁止用少数已到达的数据冒充整日更新完成。

行情日期、财务报告期和信息实际可用时间分开记录。财务与事件字段按当时已发布的信息进入因子，不因导入了完整历史文件就默认不存在前视问题。历史修订保留数据版本；回放结果能够找到原始快照。

接入流程：数据源适配 → 字段映射与单位/时点检查 → 增量导入到暂存区 → 完整性校验 → 提交可用数据版本 → 评分任务。业务页显示可用日期与异常摘要，维护页定位失败字段和同步任务。

首版可先实现标准增量文件导入，但设计数据源适配边界；真正的数据库/API 连接要按企业可提供的数据源落实。没有已接入的更新来源，交付只能称为离线选股版，不能称为自动更新的日常服务。

## 10. 最小内部边界

| 模块 | 输入 → 输出 | 关键要求 |
|---|---|---|
| 数据服务 | 源数据 → 可评分快照、字段与质量清单 | 失败导入不破坏上一个可用版本 |
| 研究服务 | 研究协议和快照 → 候选方案、反馈与验证记录 | 有限预算、检查点；不直接写当前生效版本 |
| 方案发布服务 | 候选包与验证记录 → 生效版本 | 版本不可变，当前指向可切换，记录生效时间 |
| 选股服务 | 生效方案、日期、配置、数据快照 → 排名、名单、贡献、快照 | 共用评分实现；相同输入重试复用结果，强制重算则保存新修订 |
| 跟踪服务 | 历史正式名单、后续行情、评价规则 → 模拟跟踪记录 | 标签成熟才评价，绝不回写原始名单 |

前端调用服务，不在页面函数内训练或搜索。研究与选股有独立队列/执行进程或明确的并发限额；提供日常评分资源优先级。运行时间需在现有机器和实际 5,000 多只股票数据上测量后承诺，本设计不虚设秒级性能目标。

## 11. 对照现有代码的差距

已查阅 `custom_backtester/app/workbench_selection.py`、`app/workbench_components.py` 和 `custom_bt/stock_selection.py`。

| 当前情况 | 影响与处理 |
|---|---|
| 选股页枚举组合回测目录，没有组合时跳转因子组合 | 企业流程依赖研究；改为读取发布后的方案目录/注册表 |
| 主导航并列 PPO、表达式回测、组合、选股等八项 | 按内部算法拆分业务；新业务入口与维护入口分开 |
| 已有固定组合评分、贡献、名单快照和历史保存 | 可作为核心迁移候选；需验证新方案契约后复用 |
| 股票池保存在策略快照的固定 codes 中 | 适合复现固定范围，尚不能代表动态全 A 股股票池 |
| 已有任务执行与结果追溯 | 可借鉴，但不等于具备发布、日常调度和资源隔离 |
| 现有缓存元数据记录 5,432 只股票，字段规模远少于用户设想的 400 多项 | 数据需求与实际可用字段需逐项核对，不能先假定全部就绪 |

这些发现来自定向代码阅读，不代表对现有交易核算和所有数据链路的全面审计。旧交易回测器在用于新研究结论之前，需要验证时序、成交、成本、持仓与收益核算；旧页面测试通过不构成这一证据。

## 12. 分期与可检查的交付结果

第一步：业务主链。完成标准数据增量导入、一个冻结方案的显式发布、真实日期评分、名单解释/导出、不可覆盖的选股记录与失败状态。初始基线的来源如实标明；业务链可用不代表强化学习研究已完成。

第二步：研究到发布。接入 PPO 和组合优化的真实反馈，保存验证证据、候选版本、发布与回退。研究完成后业务用户无需重走算法步骤即可用新版本选股。

第三步：持续运行。按实际数据源实现自动更新与评分、发布后模拟跟踪、周期性研究触发；再根据企业需要增加已验证的方案配置和真实交易评价接口。

最终验收场景：

1. 普通用户无需进入研究页面即可打开、生成、解释和导出正式名单。
2. 研究任务运行或失败时，当前可用方案仍能评分，已保存名单仍可查看。
3. 数据缺失或过期不会被标成今日完整结果；修复后能够重试。
4. 同一结果可追溯到方案、配置、实际股票范围、数据和实现版本。
5. 换版有生效边界；历史档案不变；回退能影响之后的新任务。
6. 页面视图过滤不会改变分数或方案正式名单；自定义子集有明确标识。
7. PPO 与组合优化的更新有执行证据；仅增加迭代计数不算反馈闭环。
8. 历史重算、历史验证、发布后模拟跟踪与企业真实成交数据在名称和口径上可区分。

## 13. 当前默认与尚需落实的外部信息

已采用的设计默认：日频收盘后评分、Top K 公共研究基准、企业侧三个业务入口、一个系统内独立维护区、首版维护者发布、不接自动交易。

实施数据接入前需确认企业能提供的文件/数据库/API、更新时点与字段字典；实施发布后评价前需固定交易与成本口径。这些信息影响对应模块落地，但不妨碍先确定本稿的业务结构。界面视觉风格与技术栈留到主页面设计阶段选择，不在本稿中承诺已完成原型。
